# RAG Portfolio Chatbot

**IT** · [Leggi in italiano](README.md)

A chatbot that answers questions about my background, my projects and the tech
stack I use, based on Retrieval-Augmented Generation: answers are generated
from the real content of my CV/README, not made up.

## Live

**https://rag-chatbot-0uwq.onrender.com** — try it directly, nothing to
download or configure. (Free tier: if it hasn't been used for a while the
first load may take a few seconds to wake up.)

## Stack

- **Backend**: Spring Boot 3 (Java 21), REST API
- **Vector store**: PostgreSQL + `pgvector` extension
- **Embeddings**: Voyage AI (Anthropic doesn't expose its own embeddings
  endpoint and recommends Voyage AI as a provider)
- **Answer generation**: Claude (Anthropic Messages API)
- **Frontend**: single HTML/CSS/JS page, no framework required

## Design decisions

Some choices I made on purpose, with the reasoning behind them — including the
things I decided **not** to build.

- **RAG, not fine-tuning.** I didn't retrain any model: answers come from
  retrieval + a prompt, not from modified weights. For a case like this, where
  the content changes (I update a file, re-ingest, done), it's the right
  choice: it costs less, I update the knowledge base in 10 minutes and I can
  cite the exact source of every answer. Fine-tuning would make sense if I
  needed to change the model's *style*, not the *information* it has.
- **pgvector on Postgres, not a dedicated vector DB.** I deliberately ruled
  out Pinecone/Weaviate/Qdrant: with a few hundred chunks I'd have added a
  service, an account and another bill for a problem that Postgres with an
  extension solves just fine. If the knowledge base grew by orders of
  magnitude I'd reconsider — today it would be complexity bought in advance
  for a problem I don't have.
- **No ANN index on the chunk table.** True story: at first I had the
  `ivfflat` index (the "right" one for pgvector) and retrieval systematically
  returned zero results even with valid data. An approximate index, tuned for
  large datasets, on a table of 15-30 rows does imprecise searches that
  sometimes find nothing. I removed it: at these volumes a sequential scan is
  instant *and exact*. I didn't read it on a blog, I found it out debugging a
  real bug.
- **Every chunk must stand on its own.** Retrieval pulls a piece of text
  isolated from the rest of the document: if I write "Project 1" without the
  full name, the model receives that piece and doesn't know what it means.
  That's why every section of the knowledge base repeats the full name of the
  project or topic, even at the cost of being redundant when you read it all
  together.
- **Two-level rate limiting, IP and session.** IP alone isn't enough (a
  corporate NAT or a VPN puts several people behind the same address), session
  alone isn't either (a cookie gets cleared). I combine them: it's enough for
  one of the two to be exceeded to block. Here too a real bug upstream: the
  first version had an off-by-one that blocked the 3rd legitimate request on a
  limit of 3 — found and fixed by checking the count by hand.
- **No second LLM acting as a judge on prompt injection.** I could have sent
  every question to a "guardian" model before answering. That doubles calls
  and costs for a risk that's low here: the bot only talks about my public
  background, has no access to sensitive data and performs no actions. Rate
  limiting + rules in the system prompt + a pre-filter with known patterns
  cover most attempts at almost zero cost.
- **The "Generate Summary" panel is hybrid on purpose.** Strengths and areas
  for growth I wrote myself, by hand, and they stay fixed: on a delicate topic
  like talking about myself and my limits I want to control exactly what's
  said, not hope the model says it well. Education, projects and stack, on the
  other hand, are generated by the LLM from the knowledge base, because
  they're objective facts where automatic generation doesn't risk writing
  something off — and meanwhile the panel shows a real synthesis capability of
  the system, not just Q&A.
- **Free tier everywhere, handling cold starts instead of paying them away.**
  Database and backend are on free plans that go to sleep after a few minutes
  of inactivity. I could have paid to keep them always on; I preferred to
  solve it with an honest loading screen (plus a periodic ping that keeps them
  awake as much as possible) instead of spending on a problem that a bit of UX
  handles for free. If this project had to handle real traffic, that's the
  first thing I'd change.
- **No frontend framework.** Plain HTML/CSS/JS, zero build step, zero
  `node_modules`. For a page of this complexity (a chat, a couple of panels, a
  few states) a framework would have added weight without adding anything I
  couldn't already do by hand.
- **Analytics without tracking people.** I store the feedback vote, the
  comment text, the questions asked — never an IP, never a session cookie,
  never anything that links two actions to the same person. It's not shyness:
  a chatbot linked to a CV gets a few dozen visits, I don't need a
  per-visitor profile, and tracking them would raise real privacy questions
  for a benefit that doesn't exist.

## Local setup guide

The link at the top is already live: this section (and the next one on
Deploy) isn't needed to try the chatbot, but for anyone who wants to run it
locally or understand how I deployed it to production.

### 1. Database

You need a Postgres with the `pgvector` extension. The fastest way is Docker:

```bash
docker run --name rag-postgres -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=ragchatbot -p 5432:5432 -d ankane/pgvector
```

Then apply the migrations (the project doesn't use Flyway: run them by hand,
in order):

```bash
psql -h localhost -U postgres -d ragchatbot -f src/main/resources/db/migration/V1__init.sql
psql -h localhost -U postgres -d ragchatbot -f src/main/resources/db/migration/V2__feedback.sql
```

### 2. Environment variables

```bash
export DB_HOST=localhost
export DB_PORT=5432
export DB_NAME=ragchatbot
export DB_USER=postgres
export DB_PASSWORD=postgres
export ANTHROPIC_API_KEY=sk-ant-...
export VOYAGE_API_KEY=...
```

Keys:
- Claude: console.anthropic.com
- Voyage AI: dashboard.voyageai.com (offers initial free credits)

Optional: `SUMMARY_STATIC_FILE` to move the file with the static sections of
the "Generate Summary" panel (default `summary.json` in the working dir).

### 2b. `summary.json` file

The "Generate Summary" feature reads the hand-curated sections (in brief,
strengths, areas for growth, logistics, contact) from `summary.json` in the
project root. It's gitignored like `content/` because it contains phrasing
about a real person. Structure: `{ "it": {...}, "en": {...} }` with the keys
`inBreve`, `puntiDiForza[]`, `doveStaCrescendo[]`, `logistica`, `contatto`.
The education/projects/stack sections are generated by the LLM from the KB.
Without this file, `POST /api/summary` returns 502.

### 3. Start

From IntelliJ (run `RagChatbotApplication`) or from the terminal with Maven:

```bash
mvn spring-boot:run
```

The frontend is served by the same backend: open **http://localhost:8080**.

### 4. Populate the knowledge base

For now ingestion is done by hand by calling the admin endpoint (in the
future you can automate it with a small script that reads all the files in
`knowledge-base/` and sends them one by one):

```bash
curl -X POST http://localhost:8080/api/admin/ingest \
  -H "Content-Type: application/json" \
  -d '{"source": "cv.txt", "text": "...your CV content..."}'
```

Repeat for each document (CV, project 1 README, project 2 README, intro text,
description of this project itself).

### 5. Try the frontend

Open **http://localhost:8080** — the frontend is a static resource served by
Spring, same origin as the APIs.

## Deploy

Stack: **Neon** (Postgres + pgvector), **Render** (backend, free tier),
frontend served by Spring, build via `Dockerfile`.

### 1. Database on Neon

1. Create a project on [neon.tech](https://neon.tech) (free)
2. In the SQL Editor: `CREATE EXTENSION IF NOT EXISTS vector;`
3. Apply the schema (from the SQL Editor paste the content of
   `db/migration/V1__init.sql` and then `V2__feedback.sql`)
4. From the "Connection Details" page get host, database, user, password

### 2. Repo on GitHub

The project goes on a Git repo (Render deploys from there). `content/` and
`summary.json` stay out (gitignored).

### 3. Backend on Render

1. New → Web Service → connect the GitHub repo
2. Runtime: **Docker** (the `Dockerfile` is detected)
3. Environment variables:

   | Variable | Value |
   |---|---|
   | `ANTHROPIC_API_KEY` | your Claude key |
   | `VOYAGE_API_KEY` | your Voyage key |
   | `ADMIN_BYPASS_PASSWORD` | a password of your choice (dev mode) |
   | `DB_HOST` `DB_NAME` `DB_USER` `DB_PASSWORD` | from Neon |
   | `DB_SSLMODE` | `require` |
   | `SUMMARY_STATIC_FILE` | `/etc/secrets/summary.json` |

4. Secret Files → add `summary.json` with the content of the local file
5. Deploy. On first start Render runs the Docker build (~3-5 min).

### 4. Populate the KB in production

```bash
BASE=https://your-service.onrender.com ADMIN_PW=... bash reingest.sh
```

(or enable dev mode from the site and call `/api/admin/ingest` by hand for
the 4 files). ~10 min for the Voyage rate limit.

### 5. Test

From a device that isn't yours, without VPN: cold start, 5-6 questions
(including a couple off-topic), feedback, "Generate Summary" IT + EN.

## Deploy notes already handled in the code

- `/api/admin/ingest` (POST and DELETE) is protected by the dev mode token
- CORS is off by default (same origin); it's enabled only with
  `CORS_ALLOWED_ORIGINS` for development with a frontend on another origin
- The port comes from `$PORT` (Render assigns it)
- The IP for rate limiting is read from `X-Forwarded-For` (needed behind
  Render's proxy)

## Security implemented

- **API keys never exposed**: `ANTHROPIC_API_KEY` and `VOYAGE_API_KEY` live
  only in the backend (environment variables); the frontend never sees them.
- **Per-IP rate limiting** (`RateLimitService`, in-memory with Caffeine):
  default 3 requests/minute and 10/day per IP, configurable in
  `application.yml` under `rag.rate-limit`. The IP is read from
  `X-Forwarded-For` when present (needed behind proxies like Render/Railway),
  otherwise from `getRemoteAddr()`.
- **Input validation**: configurable maximum length (default 300 characters,
  `rag.input.max-length`), checked **before** calling embedding or LLM, to
  avoid wasting tokens on abusive or overly long input.
- **System prompt hardening**: the prompt in `ChatService` instructs the
  model to ignore prompt injection attempts, not to leave the professional
  context and not to reveal the system instructions themselves. Realistic
  note: no prompt hardening is 100% impenetrable, but combined with rate
  limiting and a character limit it drastically reduces the surface and the
  convenience of an attack.

## Privacy and data collected

For improvement and performance monitoring purposes the system stores
**only**:

- the **text of the questions** asked to the chatbot, to understand what's
  asked most often — with nothing linking them to who wrote them;
- the feedback **rating** and the optional **comment text**.

Nothing else is stored: no IP address, no personal data, no identifier that
would allow linking two actions to the same person. The `question_log` and
`feedback` tables don't even have a column for the IP or the session.

The only cookie is `rag_session_id`, a random identifier used **exclusively**
for rate limiting (preventing the same session from exceeding the request
limit): it contains no personal information and isn't used to track browsing.
The IP address too is used only for rate limiting, in memory and on the spot,
and is never written anywhere.

## Transparency features (for the technically-minded)

- **Source citation**: every answer includes the list of retrieved chunks
  (`sources` in the JSON response), with source file, text snippet and cosine
  similarity score. In the frontend it's shown in an expandable "source (N)"
  panel under each answer.
- **Vector query inspection**: the "inspect vector query" switch at the top
  shows, for each answer, the embedding model used, the generation model, the
  `top-k`, and retrieval/generation times in milliseconds (`debug` in the
  JSON response).

## Possible future extensions

- Hybrid search (full-text + vector) for the exact names of
  frameworks/libraries that embedding alone sometimes generalises
- Response streaming (Server-Sent Events) instead of waiting for the full
  answer
- Configuration-driven architecture: making identity, rules and content
  external configuration, so the same code serves different chatbots

## How it was built

This project was built in pair with a coding agent (Claude Code). The
architecture decisions (splitting the keep-alive endpoints so as not to burn
the database's free resources, privacy-by-design in the logs, two-level rate
limiting), spotting and diagnosing the bugs — like the `ivfflat` index
returning zero results, or the off-by-one in the rate limiter — and
validating every choice are mine; the AI sped up writing the code. The goal
was to use AI where it saves time, on repetitive code and boilerplate,
without delegating the reasoning to it.
